# Gift Factory Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Create and immediately publish an unclaimed Cover gift from `/admin` in under 20 seconds, with optional private media and an in-place success state.

**Architecture:** A protected server action validates input and optional uploads, then invokes one service-role-only database transaction for profile, existing gift claim, links, presentation, and publication. Gift files live in a private bucket at stable internal paths; public delivery uses slug plus asset type and resolves only a currently published profile's referenced object. A compact Gift Factory route provides create, list, and unclaimed edit details without changing customer onboarding.

**Tech Stack:** Next.js App Router, React server actions, Supabase Postgres/Storage, TypeScript, Vitest.

**Spec:** `docs/superpowers/specs/2026-09-26-gift-factory-design.md`

## Global Constraints

- “Do not add another gift schema, modify normal customer onboarding, migrate files when a gift is claimed, or change media paths on ownership transfer.”
- “Every gift uses template `cover`, `profiles.owner_id = NULL`, the existing `profile_gift_claims` infrastructure, a Cover presentation, and supplied links.”
- “Public media is addressed by public profile slug plus asset type (portrait or cover), never by a caller-supplied storage path.”
- Never expose service-role credentials, recipient email publicly, or internal gift-media object paths to the browser.
- Read the applicable Next.js agent guide under `node_modules/next/dist/docs/` before writing any product code; current Next.js conventions differ from assumptions.
- Follow current Supabase documentation and migration conventions; use `supabase migration new` to create the migration file.

## Review Focus

- Concurrent creates for similar names: database uniqueness must prevent duplicate slugs without overwriting an existing profile; test collision allocation.
- Spoofed/non-admin server-action submissions: require admin identity before storage or database operations; test zero privileged calls for denied requests.
- Upload succeeds but a later upload or transaction fails: remove all attempt-owned objects, never report success, and keep private leftovers unservable if cleanup fails; test cleanup.
- A draft, wrong asset kind, unknown slug, or unreferenced media: return not found and never download arbitrary object paths; test each category.
- Claiming changes owner but must not change media object paths: test the existing claim flow and migration behavior.
