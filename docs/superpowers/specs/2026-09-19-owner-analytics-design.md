# Owner analytics design

## Goal

Give each IQ Card owner a real seven-day view of the activity generated by
their published profile and physical card:

- profile views;
- NFC card taps;
- contact saves;
- external-link clicks;
- a daily seven-day trend and totals.

The implementation must not collect visitor names, contact details, IP
addresses, user agents, or cross-site browsing history.

## Event model

Add `profile_analytics_events`, a service-managed append-only event table.
Each row has a profile id, event type (`profile_view`, `card_tap`,
`contact_save`, or `link_click`), an optional profile-link id, its UTC day,
and timestamps. Browser-originated events also have a one-way daily visitor
key hash. That hash comes from a random first-party browser token and a server
secret; the raw token never reaches the database.

The database enforces one browser-originated event per profile, event type,
link, visitor hash, and UTC day. This makes profile views and clicks useful
without silently inflating the owner dashboard on page reloads. Card taps are
recorded by the tap redirect itself and are not deduplicated: each physical
tap is meaningful activity.

No client can insert or read analytics rows directly. Security-definer RPCs
validate the event shape and published-profile/link ownership. Owners query
only their own aggregated results through a server-side repository.

## Card tap links

Add `profile_tap_tokens`, with one active, random, opaque token per saved card
design. The database stores only a SHA-256 hash of that token, the target
profile, the design id, lifecycle timestamps, and its active state.

`/t/[token]` resolves an active token, records a `card_tap`, and redirects to
the profile's public URL. Unknown, revoked, draft, or unpublished mappings
return a normal not-found response and never disclose a profile.

The Card Atelier dashboard module shows the owner a copyable NFC tap URL. This
URL must be written to the physical card's NFC chip during fulfillment or by
the owner; creating the URL alone cannot change a physical card already in the
world.

## Public-profile instrumentation

Public profiles receive a small client-side tracker that sends a profile-view
event only once the page is visible. This avoids counting server render work
and most prefetches as views.

The existing contact-save control records an event with `sendBeacon` (with a
fetch keepalive fallback) before following the vCard URL. Each public external
link does the same for its own link id before opening the destination. Tracking
must fail open: visitors can always save a contact or follow a link even when
analytics is unavailable.

## Dashboard

Add an owner-only analytics repository that returns the last seven UTC days,
zero-filled, plus totals for the four event types. The Live Owner Center
replaces its current placeholder with:

- totals for profile views, card taps, contact saves, and link clicks;
- a compact seven-day daily trend;
- an accurate empty state when all totals are zero.

The existing content, card, and profile editor actions stay independent of
analytics. Spaces and Requests & Updates remain clearly marked as future
features.

## Failure handling and operations

Tracking endpoints return a safe success response for malformed or duplicate
browser events so public interactions are never blocked. Server logging keeps
operational errors without storing visitor identifiers. The migration creates
the required indexes and restrictive RLS/grant boundaries; dashboard reads use
the authenticated owner id, never a caller-supplied profile id.

## Verification

Tests cover:

- migration security, constraints, and indexes;
- token resolution and unpublished/revoked behavior;
- event validation and daily deduplication;
- analytics aggregation and zero-filled seven-day output;
- profile-view, link-click, and contact-save client instrumentation;
- tap redirect behavior;
- dashboard totals, trend, and zero state.

Browser verification covers a real public profile view, a link click, a
contact save, a card-tap redirect, and the resulting owner dashboard values.
